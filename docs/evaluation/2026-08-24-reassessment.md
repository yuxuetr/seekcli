# 复评：SeekCLI × DeepSeek Harness

> 评估时间：2026-08-24
> 被评估方：SeekCLI `main` @ `e2cdc0a`（阶段二十 ~ 三十三推进完毕）
> 基线：[2026-08-22 首评](2026-08-harness-gap-analysis.md)
> 对照基准与评分口径未变，见 [scoring-rubric.md](scoring-rubric.md)

---

## 0. 结论

| 口径 | 首评（08-22） | 复评（08-24） | 判断 |
| --- | --- | --- | --- |
| A. 纠偏机制（单次调用内的 harness 机制） | 85% | **95%** | 本就最强，补齐了取消传播与可测性 |
| B. 组件全景（对照 dsh 的组件清单） | 45% | **80%** | 主要增量，MCP 与事件日志是分水岭 |
| C. 产品形态（别人能否装上、扩展、集成） | 25% | **70%** | 从「只能作者自用」到「装得上、扩得动」 |
| **整体** | **约 40%** | **约 80%** | |

**首评的三处「架构级欠账」全部结清**：

| 首评判断 | 现状 |
| --- | --- |
| L4 会话是状态快照而非事件日志——**唯一建议推倒重来的地方** | append-only `events.jsonl`，`derive_messages` 是工作集唯一来源；fork / resume / 检索 / 标题全部由日志派生；69 个历史会话已迁移 |
| L2 工具面既窄又封闭，无 MCP | 15 个内置工具 + 任意 MCP server；外来工具走同一道策略门 |
| L5 一切在编译期定死 | 工具面靠 MCP 扩、定时任务靠 `TASK.md` 扩，两者都不需要改 Rust |

**没变的**：SeekCLI 仍然是单人 Rust CLI，仍然不做沙箱、Web UI、插件框架、workflow 编排。
这些是[写明理由的取舍](../architecture/design-principles.md#2-明确排除的复杂度)，
不是欠账——复评没有因为「dsh 有」而给它们扣分。

## 2. 逐层复评

| 层 | 首评 | 复评 | 关键变化 |
| --- | --- | --- | --- |
| L0 基底 | 70% | **100%** | provider 配置化（可指任意兼容端点）、重试退避 + 两级超时、token 计数取代字节 |
| L1 引擎 | 80% | **90%** | 取消真正传到子进程；主循环 524 → 339 行；**首次具备端到端可测性** |
| L2 边界 | 45% | **85%** | 原生 glob/grep、统一执行管线 + 结构化 `ToolResult` + per-tool 超时、后台 job、`ask_user_question`、MCP |
| L3 安全 | 50% | **80%** | 统一策略门（模式→路径→命令）、子命令逐条取最严、越界写检测、审计日志 |
| L4 记忆 | 45% | **90%** | **事件日志重构**：resume / fork / search / O(1) history / 压缩事件化 / blob 归属 |
| L5 组合 | 40% | **65%** | **MCP 落地**；子代理仍是一次性（L5-2 开放） |
| L6 界面 | 35% | **75%** | 通用 headless（`-p` / stdin / `--output json` / 退出码）、配置定位修复、输出分流 |
| L7 可观测 | 55% | **95%** | **录制/回放**让主循环首次可测、eval 26 任务、覆盖率门禁真正生效、trace 加 `verdict` |
| L8 循环 | 60% | **90%** | 任务声明式化（`TASK.md`），新增任务不改代码 |

### 仍然开放的 4 项

| 缺口 | 内容 | 状态 |
| --- | --- | --- |
| L1-1 | 循环无正式扩展点（`LoopHook`） | 等第二个用户出现 |
| L1-2 | 无 turn / step 模型 | 收益仅「概念更清晰」，暂不做 |
| L1-4 | 中断后上下文可恢复，**任务**不自动续跑 | 约 30 行的独立小改动 |
| L5-2 | 子代理一次性，无法续跑 / 通信 | 完整方案需要 mailbox 与生命周期管理 |

## 3. 产品形态（C 口径）为什么涨得最多

首评这一项 25%，是三个口径里最低的。当时的判断是「基本只能作者自用」。

| 项 | 首评 | 复评 |
| --- | --- | --- |
| 配置文件位置 | ❌ 读写当前目录（缺陷级） | ✅ `~/.seekcli/` + 项目级覆盖 + `$SEEKCLI_CONFIG` |
| 凭证管理 | ❌ 只认一个环境变量 | ✅ `env:` / `file:` 前缀，**字面量 key 拒绝启动** |
| 分发 | ❌ 无产物、单平台 | 🟡 四平台产物 + 校验和 + crates.io 元数据齐备，**发布动作待执行** |
| LICENSE | ❌ 声明 MIT 但无文件 | ✅ |
| 贡献治理 | ❌ 无 | ✅ CONTRIBUTING + 两个 issue 模板 |
| 自身 agent 指令 | ❌ 读别人的 AGENTS.md，自己没有 | ✅ |
| 可扩展性 | ❌ 只能改源码 | ✅ MCP（工具）+ `TASK.md`（定时任务） |
| 可集成性 | ❌ 无 headless | ✅ `-p` / stdin / `--output json` / 退出码语义 |

**未达 100% 的原因**：发布未执行（🟡），且无编辑器集成通道（L6-3 待重估）。

## 4. 一处方法学收获

首评把缺口分成两桶——**已排期**与**明确不排期**。推进完之后核对发现，
这个模型少了一个桶：**「没做完，但也不是不做」**。

L1-1 / L1-2 / L1-4 / L5-2 就落在这个缝里，于是它们只能悄悄留在层文档的表格里，
而路线图上看不见。更糟的是 L7-1 / L7-4：**工作早已完成，缺口表却还开着**，
因为没有任何东西比对「层文档说的」和「路线图做的」。

修法是把模型改成三桶，并把 `scripts/check-gap-coverage.py` 从双向扩成三向校验。
已反向验证：把已完成的 L7-1 改回开放状态，校验器立即失败。

> **教训**：缺口清单的结构决定了什么问题能被看见。少一个状态，就少一类可发现的漂移。

## 5. 与 dsh 的差距现在在哪

规模差距（14k vs 56.5 万行）**不是本次评估的扣分项**——那是团队产品与单人 CLI 的
体量差异。按组件清单看，剩余真实差距只有三类：

| 差距 | dsh | SeekCLI 的取舍 |
| --- | --- | --- |
| **可替换性** | 一切是插件，连 agent loop 都能换 | 编译期组合 + MCP。插件框架的复杂度收益比在单人 Rust CLI 上不成立 |
| **执行世界抽象** | capability seam 让一次 provider 切换把 Bash/PTY/LSP 一起搬到远程沙箱 | 无此需求：本地 CLI 只有一个执行世界 |
| **生成式文档** | tool-catalog / module-graph 等 5 类自动生成 + CI 新鲜度门禁 | 手写 17 篇，但**链路有机械校验**——形式不同，防漂移的目的一致 |

前两条已在 [design-principles §5](../architecture/design-principles.md#5-与-deepseek-harness-的边界)
的三问检查表下判定为不对齐。第三条是 SeekCLI 可以借鉴但当前规模下收益有限的。

## 6. 方法学说明

- 与首评同源同法：dsh 侧结论来自其自述文档与生成产物，未逐包读源码；
  SeekCLI 侧来自全量源码 + `git` 历史 + 实跑 `cargo test` / `llvm-cov` / `deny`。
- 分数是**相对 dsh 这个坐标系**的组件完成度，不代表绝对质量。
- 所有「已落地」的判断都对应一次真实端到端验证（见各阶段提交信息），
  而非只看单测通过。
