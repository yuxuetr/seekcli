### 2.1 真正的分水岭是第 5 与第 6 连通了

三评写过：「第 5 条是分水岭——变异若无法被机器判定好坏，其余六条做得再好
也只是『可编程』，不是『可进化』。」

当时两条都在，但 `bench.rs` 与 `accept` 之间**零调用关系**。现在：

```text
harness_inspect{what:"mcp"}  →  发现能力缺失
propose{kind:"mcp"}          →  起草
/propose list                →  校验（能不能落地）
/propose accept skill <n>    →  跑冒烟集两遍，回归即拒绝并点名
```

**这是本轮唯一一处结构性变化**，其余都是把已有的东西接上或补齐。

### 2.2 第 2 条为什么停在 🟢 而不是 ✅

代码级自修改（dsh 的 dynamic package）**明确不做**，理由未变：Rust 没有安全的
运行期加载，等价需求由 MCP 的进程边界满足。所以这一条的上限就是 🟢——
**这是取舍，不是欠账**，D 口径不应因此给满分。

## 3. 一处可以对 dsh 说的话

三评判断「把 eval 接进提案闸门」是 SeekCLI 能领先 dsh 的地方，理由是
dsh 的测试在 CI 里跑、不在会话里跑。现在它落地了，而且**实测比预期更窄**：

只有 `skill` 提案能被 eval 衡量。`mcp` 要重启才连上、`task` 是给调度器的提示词——
对它们跑 eval 是表演。这个收窄不是退让，**是让这句话变得真实**：
一个对三分之一情形有效、并明说另外三分之二为何无效的闸门，
比一个号称全覆盖实则大部分在空转的闸门强。

## 5. 方法学收获：设计稿与代码的接触面

三评的收获是关于**缺口清单的结构**。本轮的收获是关于**设计稿本身的可靠性**。

本轮写了 6 份层文档设计，其中 **3 份在实现时被证伪或需要实质修正**：

| 设计稿说 | 代码说 | 谁抓到的 |
| --- | --- | --- |
| 「75 处构造点一行不改」 | Rust 字面量必须写全字段，34 处各加一行 | **编译器** |
| 「trajectory 导出是 SessionStore 的第二个用户」 | 它是导出格式，不是存储后端 | 动手前的调研 |
| 「跑相关 eval 套件」（不分类型） | mcp / task 根本测不到 | 动手前的调研 |

外加一次**实现到一半主动回退**（41.4 的 MCP 透传）：当时三个候选方案都要在
「所有工具走同一条守门路径」上开缝。停一轮之后找到了第四个——改闭包的输出
类型而不是每个工具的签名——比原来三个都干净。

> **教训：设计稿的价值不在于它正确，在于它具体到足以被证伪。**
> 三次被推翻的都是**具体的断言**（「75 处」「第二个用户」「相关套件」）；
> 如果当时写的是「妥善处理构造点」「为将来扩展留出接口」，
> 就不会有任何东西能推翻它们，而错误会一直留到代码里。

推论有两条，都值得带进下一轮：

1. **设计稿要写得可被证伪**，不要写成不可反驳的正确废话。
2. **动手前的调研要算进设计阶段**，不是实现的开始——本轮两次推翻都发生在
   调研阶段，代价是零；如果发生在实现完之后，代价是一次返工。

另有两次由 `check-gap-coverage.py` 抓到的漂移（勾掉 34.1 时 L1-6 失去归属；
三评新增的 L7-7 / L7-8 未挂到阶段上）——那个脚本在本轮的实际拦截次数是 **2**。

## 6. 附记（2026-09-13 晚）：发布把两个「一直是坏的」暴露出来

推 `v0.2.0` 时才发现 `build` 从 **2026-07-17** 起就一直是红的，三次失败同一个原因：
`/copy` 的 `use std::io::Write;` 写在模块级，而它唯一的用处在
`#[cfg(target_os = "macos")]` 块里——于是在 Linux 上是死导入，`-D warnings` 判为
编译失败。修掉后 tag 构建通过，Release 却只出三个平台：`aarch64-unknown-linux-gnu`
挂在 `openssl-sys` 上，因为 workflow 装的 `gcc-aarch64-linux-gnu` 是**链接器**，
而 openssl 要的是 aarch64 的 **libssl 这个 C 库**——这一格从加进矩阵那天起就没成功过。

改用 rustls 一并解决，并顺带修掉一个此前无人察觉的发布缺陷：native-tls
**动态链接构建机的 libssl**，所以已发出的 Linux 产物在 libssl 版本不同的发行版上
起不来。「发布了二进制」和「那个二进制能在别人机器上跑」是两件事。

### 6.1 方法论上真正的收获

两次失败共用一个形状，而且**都不是「缺少门禁」**：

- `check` job 就跑在 Linux 上，两个月里每一次都**正确地报了**那行死导入；
- aarch64 那一格的失败也是 CI 如实报出来的。

缺的是**有人去读门禁的输出**。而本地在 macOS 上怎么跑都是绿的——那台机器
**结构性地看不见**这两个错误。三评、复评里所有「零警告基线」的说法，
因此都只在一个平台上成立。

这与 §3 记的那条是同一件事的另一面：那里是「设计稿具体到足以被证伪」，
这里是「**门禁的输出必须被读，否则它等于不存在**」。一条没人看的红线，
和没有这条线，对项目的作用完全相同。

**可操作的推论**：

1. 声称「零警告 / 全绿」时必须说清**是在哪个平台上**——不写平台的断言是空的。
2. 推送后 `gh run list` 看一眼，比再加一道本地门禁便宜得多，也可靠得多。
3. 跨平台的东西要在**目标平台上**验证。本次是用 `zig cc` 当交叉编译器在本地
   真跑通 aarch64 release 构建、检查产物动态依赖，再用真实 API 调用确认
   rustls 握手可用——换 TLS 后端属于「编译不会失败也不会 panic」的改动，
   只看编译过不算验证。
