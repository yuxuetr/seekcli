> 评估时间：2026-09-15
> 被评估方：SeekCLI `main`（阶段四十一完成后）
> 基线：[2026-09-13 四评](2026-09-13-fourth-assessment.md)
> 坐标系：**E 口径（真实使用）**——前四评都在问「建成了什么」，本次问「用上了什么」

> 而且错得关键——见 [§1.5](#15-更正真实使用不是没有过而是在特定一天停止)。

> 变成**恢复一项已被证明在用的能力**。首版错在只看了按创建时间排序的
> 最近 30 条会话标题——那 30 条恰好全在冒烟期内。

## 0. 结论

**工程完成度与使用度之间存在数量级落差。** 前四评的所有结论都成立，本次不推翻任何一条。
本次新增的是一个此前四轮都没有量过的维度：

| 口径 | 09-13 四评 | 本次 |
| --- | --- | --- |
| A. 纠偏机制 | 98% | 98%（未复核，无理由变化） |
| B. 组件全景 | 85% | 85%（同上） |
| C. 产品形态 | 75% | 75%（同上） |
| D. 自进化地基 | 约 75% | 约 75%（同上） |
| **E. 真实使用** | — | **约 5%** |

E 口径不是「产品形态」的重复。C 问的是「能不能被别人装上跑起来」（四平台产物、
安装路径、文档），答案是能。E 问的是「作者本人日常是否在用」，答案是否。

> **不是「做了个没人用的工具」，是「工具被日常使用过，而使用停止于它赖以工作的

## 2. 一处需要更正四评的表述

四评 §4 写：「五项没有一项是『忘了』——每项都有写明的理由。」这句**事实正确但归因不全**。

`LoopHook` 无第二用户（L1-1）、`SessionStore` 立项理由被推翻（L4-7）、
`allowed_tools` 停在「phase 12.5 will wire」（L5-7）——四评把它们各自归因为独立的取舍。
本次核查给出一个更简单的共同解释：

> **它们缺的不是判断，是真实负载。** 判据「出现第二个实现时翻转」本身没问题，
> 问题是零真实使用的情况下，连第一个实现都不会出现。

这不削弱四评的结论，但改变了下一轮该做什么：**再做第五轮自评是边际收益最低的动作。**

## 4. 方法学收获

前四评的方法是**读代码与文档，对照缺口清单打分**。这套方法有一个盲区：
它衡量的全部对象都在仓库里，而仓库里不会记录「作者今天没有用它」。

本次只多做了一件事——**读 `~/.seekcli/` 而不是读 `src/`**。运行时目录是产品与用户
之间唯一的接触面，它记录的是行为而不是意图。审计日志、会话标题、配置文件的
修改时间、proposal 的数量，这四样东西在任何自评里都不会出现，但它们是
E 口径唯一的证据来源。

**建议纳入后续评估的固定动作**：每轮自评先核查运行时目录，再读源码。
如果运行时目录是空的，那一轮评估的其余部分就只是在衡量一个没人用的东西建得有多好。

## 5. 本次评估自身的错误（2026-09-16 补）

首版结论「真实使用记录为零」是错的，错因值得记下来，因为它与本评估要批评的
毛病是同一个：

**只看了一个排序后的窗口，就当成了全集。** §1.2 取的是按创建时间倒序的前 30 条
会话标题——而冒烟期恰好覆盖了最近 32 条，于是窗口里一条真实会话都没有。
全量 76 条一跑，44 条真实，画面完全不同。

代价不只是数字错了。首版据此写了「D 口径的缺口共同解释是缺少真实负载」，
那句话方向仍对，但**漏掉了更有用的一半**：负载不是没来过，是被一次重构挡掉了。
少了这一半，阶段四十三看起来像一个合理的猜测；有了这一半，它是一条有日期、
有提交号、有原始 prompt 的证据链。

**教训与 §4 同源**：读运行时目录是对的，但要读全，而且要按**时间序列**读而不是
按最近读。一个「最近全是测试」的目录和一个「一直只有测试」的目录长得很像，
区别只在更早的地方，而那正是排序会藏起来的位置。

## 6. 阶段四十五补记：一条被加剧的既有缺口（L4-12）

design-principles §3 写着：

> **模型可见 = 已记录**：任何进入模型请求的内容必须能从 `events.jsonl` 重建。

`chat` 的流程是「从事件日志投影出 `messages` → `ensure_agent_system_prompt`
往里插系统消息」。插进去的东西**不回流到日志**：

| 注入物 | 可从日志重建？ |
| --- | --- |
| 静态 kernel | ✅ 常量 |
| `research_rules` | ✅ 常量（是否注入由配置决定，可推） |
| `workspace_rules` | ❌ 取决于当时 cwd 的 `AGENTS.md` 内容 |
| 记忆注入（阶段四十五新增） | ❌ 取决于当时 `~/.seekcli/memory/` 的内容 |

**这不是阶段四十五引入的**——`workspace_rules` 早就在违反。但阶段四十五加了
第二个不可重建的来源，而且是一个**会随时间变化**的来源（偏好被接受、领域条目
被写入），所以「同一个会话重放会得到不同的 prompt」从一个边缘情况变成了常态。

诚实的处理是记成缺口而不是顺手扩大本阶段的范围。**顺手修它有个不明显的坑**：
把注入记成 `SystemPrompt` 事件后，下一轮投影会带出它，而记忆变化时会追加一条
新的——旧的那条按 append-only 的规矩不能撤回（与 `commands.rs` 对 skill 激活
的处理同理），于是 prompt 里会堆积历史记忆快照。**要么接受这个堆积，要么让投影
对某类事件只取最后一条**，后者是投影语义的实质变更。排进阶段四十七与 Run 身份
统一一起做，那一阶段本来就是在处理「记录是否完整、能否归因」。

## 7. 第四轮的真实验收（2026-09-16 晚）

DeepSeek 密钥恢复后跑通的实测。**四批此前挂着「未验证」的东西全部落地**，
并且其中一次差点被一个平凡的错误骗过去。

### 7.1 阶段四十三：重放 2026-05-02 那条失效的 prompt

`智谱(Zhipu AI)最近有什么值得关注的消息？请给出来源链接和发布时间。`
—— 与 `@web 智谱的股价现在是多少？` 同类，那条自阶段七起就答不了。

6 轮，`web_search` ×4、`web_fetch` ×8（多次并行），86K prompt / 99% cache hit。
引用契约**逐条自发落实**，不是被提示词逼出来的：

| 契约要求 | 模型实际输出 |
| --- | --- |
| 区分摘要与原文 | 「这条我**没有打开原文核实**……请当作待验证线索而非事实」 |
| 取不到原文要说明 | 「付费墙，我只读到导语」 |
| 时效性口径 | 「『当前』的边界：以上覆盖 8 月下旬至 9 月 16 日」 |
| 来源可核 | 每条结论带 URL + 发布日期 |
| 单方面说法标注 | 「这是 Anthropic 单方面指控，我未找到智谱的公开回应」 |

### 7.2 阶段四十五：记忆

- 记忆索引 → `memory{action:"read"}` → 发现条目已存在 → **拒绝重复写入**。
- 两条经闸门接受的偏好被遵守：回答用中文、技术术语用英文。
- 记忆 blob 内容与注入完全一致（偏好内联、`ielts` 只列名字与条数）。

### 7.3 阶段四十七：全部四项

```text

  turn 0   meta {"seq": 3}      ← 日志 seq=3 正是本轮第一条 AssistantMessage
  turn 1   meta {"seq": 5}      ← 日志 seq=5 同理
```

### 7.4 方法学：一次差点成功的假验证

头两次实跑里，trace 的 join key 和 `ContextInjected` **都没出现**。
差一点就得出「47 的实现有问题」的结论——

**真实原因是二进制比源码旧了近十小时。** 阶段四十七之后我只跑过 `cargo test`
与 `cargo clippy`，没跑 `cargo build`，而端到端用的是
`~/.target/debug/seekcli`。`stat` 一下就看见了：10:36 vs 20:21。

这条与 §5 的教训同源，也与四评 §5「设计稿与代码的接触面」同源：
**验证的对象必须是你以为的那个对象。** 一次「功能没生效」的观察，
和一次「跑的是旧二进制」的观察，现象完全一样。

**已纳入习惯**：端到端实跑前先 `cargo build`，或直接看二进制时间戳。
