## 0. 结论

**内核健康，边界清楚，单点债务集中在一个函数上。**

## 2. 分层：成立

L0–L8 不只是文档上的说法，代码里对得上：

| 层 | 模块 | 边界是否被跨越 |
| --- | --- | --- |
| L0 基底 | `api/` | 否。四个 `LlmProvider` 实现全是装饰器 |
| L1 引擎 | `engine.rs` | 否，但内部拥挤，见 §3 |
| L2 工具 | `tools/` | 否。**一条守门路径**，MCP 与内置同路 |
| L3 安全 | `tools/policy.rs` `approval.rs` `path_security.rs` | 否 |
| L4 记忆 | `session.rs` `history.rs` `memory.rs` `agent/compressor.rs` | 否 |
| L5 组合 | `skills.rs` `subagents/` `mcp/` `proposals.rs` | 否 |
| L6 界面 | `main.rs` `commands.rs` `ui.rs` | 否 |
| L7 可观测 | `observability/` | 否。装饰器 + 边界埋点，主循环里无计费/重试/录制代码 |

**最值得肯定的一条结构约束**：`tools/mod.rs` 的
`parse args → policy gate → deadline → execute → audit` 是**唯一**路径。
MCP 工具走 `execute_with` 进同一条管线——**一个来自配置的能力，
没有绕过 `--read-only` 的路**。阶段四十三新增的两个出网工具也自动落在里面。

## 3. 内聚：一处例外，且是本轮新增的

多数模块能用一句话说清自己回答什么问题，且模块头的自述与实现一致：

```text
memory.rs     跨会话要记住什么
session.rs    这次会话发生过什么（append-only）
policy.rs     这次调用允许吗
proposals.rs  模型自己写的改动，谁来批
web.rs        怎么从网上取东西并把它当数据对待
```

**例外是 `engine.rs`**：它同时承担

1. ReAct 主循环（L1 本职）
2. 工具面装配
3. 子代理委派
4. 系统提示词组装
5. journal 落盘与记账

五件事挤在 2,128 行里，其中 `run_agent_loop` 一个函数 431 行。

### 3.1 这条债是本轮加的，且是我加的

阶段三十一把主循环从 **524 → 339 行**并写进了层文档。
阶段四十二 ~ 四十八又加回 **134 行**：预算检查、skill 裁剪、两个 journal
落盘点、trace 注解、ChildRun 记录。**每一处单看都有理由，合起来就是回潮。**

本次已抽出**工具面装配**（473 → 431 行）。选它而不是别的，理由是它是
唯一一条**真实的缝**：输入 `(tools, depth)`，输出 `Vec<Tool>`，与循环状态无关。
回报是装配顺序这条性质终于能单测——**裁剪必须作用于整个工具面**
（所以排在 MCP 与 research 工具之后），这在 470 行的循环体里没法验证。

**剩下的 431 行不建议继续拆。** 其余部分共享大量循环状态
（`messages` / `events` / `turn_had_failure` / `plan_next` / 三个终止标志），
拆出去要么传一个巨大的参数包，要么建一个持有全部状态的结构——
两者都是把耦合从「一个长函数」搬到「一组互相知道对方内部的小函数」，
**不减少耦合，只减少行数**。这正是 AGENTS.md「工程品格」要拒绝的那种拆分。

**何时重估**：当主循环里出现一段**不碰终止标志、不碰 `messages`** 的逻辑时。

## 4. 耦合：11 个全局，有条件的可接受

```text
policy::MODE          approval::POLICY / INTERACTION    shell::INTERRUPT
offload::BLOB_DIR     provenance::SOURCES               web::BACKEND
jobs::JOBS            cost::RATES                       ui::HEADLESS
```

**这不是欠债，是「单进程、单运行、单用户」这个事实的诚实表达。** 证据：
子代理与父运行**应当**共享 policy mode、blob 目录、来源记账——
把它们收进 RunContext 反而要再写一遍「子作用域继承父作用域」的逻辑。

代价是真实的：测试需要 `testsync::lock()` 串行化，而且**同进程并发多个 Run
会互相污染**。

**何时重估**：需要同进程并发运行多个 Run 时（最可能的触发点是 eval 并行化——
现在 7 个套件串行跑，`research.json` 一轮 33 秒）。

## 5. 完整性：未发现「框架搭好、逻辑没写」

按 AGENTS.md 新写的判据逐项查了一遍，**没有找到只有壳的抽象**。
几处「看起来像半成品」的，实际都带着诚实的标注：

| 项 | 状态 | 判定 |
| --- | --- | --- |
| `Skill::version` | 记录，不强制 | **合格**。是回滚的前置，L5 §4.6 写明「记录不强制」 |
| `MAX_SUBAGENT_DEPTH = 3` | 守一条走不到的路 | **合格**。是「子代理不得嵌套」的第二道防线，成本为零，阶段四十八写明了 |
| `LoopHook` | 不存在 | **合格**。判据明确：有第二个用户再抽 |
| `pro_model` | 只有 `/model pro` 能到 | **合格**。有真实入口 |
| `Frontmatter::version` | 曾「解析但不消费」 | **已修**（阶段五十接进 `Skill`） |

**唯一真正被判过「名实不符」的那类问题（解析了不生效、日志自称 append-only 实为重写、
闸门只在开发机生效），本轮全部结清**——见五评 §3 的九个缺口。

## 6. 风险排序

| # | 风险 | 严重度 | 现状 |
| --- | --- | --- | --- |
| 1 | **真实使用仍然很薄** | 高 | 今天 6 次真实运行，此前 4 个月为 0。所有「有效」的判断都建立在这 6 次上 |
| 2 | **费用上限是调用数，不是钱** | 中 | `max_llm_calls_per_run = 150`。flash 便宜，换贵模型时这个数字的含义会变 |
| 3 | `engine.rs` 集中度 | 中 | 见 §3，已部分缓解 |
| 4 | **层文档完成度过期** | 低 | 九份层文档的百分比写的是「阶段二十 ~ 三十二后」，现在是阶段五十 |
| 5 | 全局状态阻碍并发 | 低 | 见 §4，有明确触发条件 |

### 6.1 第 1 条为什么排第一

阶段四十九建了 `research.json`，5 条任务写自**观察到的真实行为**。
但它们观察的是**同一天的 6 次运行**。一个套件能防的是**回归**，
不是**覆盖不足**——而现在的覆盖面就是那 6 次。

**这不是再写代码能解决的问题。**

## 7. 建议

**不做**（当前版本，理由见阶段四十八评估）：`lib.rs`、RunContext、
继续拆 `run_agent_loop`、统一扩展生命周期。四项的共同理由是**没有第二个消费者**，
且四项都写明了重估条件。

**做**，按顺序：

1. **用它两周**——第 1 条风险只有这一个解法。
2. 每周跑一次 `--bench examples/benchmarks/research.json`（≈¥0.06），
   看引用契约有没有退化。
3. 撞到墙就记下来，转成 eval 任务。**真实失败样本现在是这个项目最稀缺的资源**，
   比任何一个未做的阶段都值钱。

### 7.1 顺带修掉的

层文档的完成度百分比已更新到阶段五十的实际状态（风险 4）。
`scripts/check-gap-coverage.py` 管的是缺口编号的归属，管不到这种数字漂移——
**这类「文档说的是 18 个阶段前的状态」是机械校验的盲区**，
与四评 §5「设计稿与代码的接触面」是同一类问题。
